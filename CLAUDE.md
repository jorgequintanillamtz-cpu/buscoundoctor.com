## 1. Qué es este proyecto

**BuscoUnDoctor.com** es un directorio médico premium para **Monterrey y San Pedro Garza García, Nuevo León, México**, con visión de escalar a otras ciudades. Conecta pacientes con médicos especialistas verificados (cédula profesional).

- El negocio depende de **tráfico orgánico (SEO)**, no de publicidad. La arquitectura de URLs, páginas y contenido está pensada para Google.
- El cuello de botella es **reclutar médicos**, no la tecnología. El registro (`/registro-medico`) es autoservicio con fricción mínima; la calidad se modera después.
- **Prelanzamiento:** el lanzamiento público es el **15 de noviembre de 2026** (se movió desde el 15 de octubre el 2026-10-02, a petición de Jorge) (`LAUNCH_DATE` en `src/lib/launchCountdown.js`). Todavía hay muy pocos médicos reales; cualquier dato que veas en producción puede ser de prueba, así que pregunta antes de borrar.

### La capa de compatibilidad `src/api/base44Client.js`

El sitio se construyó primero en Base44, y ~240 archivos llaman al SDK con la sintaxis de Base44 (`base44.entities.Specialist.filter(...)`, `base44.auth.*`, `base44.functions.invoke`, `base44.integrations.Core.*`). En vez de reescribirlos, `base44Client.js` **traduce esas llamadas a Supabase**. Entonces:

- Sigue usando `base44.entities.X` en el código nuevo; no llames a `supabase` directo salvo dentro de esa capa o de `src/lib/`.
- Una tabla nueva debe agregarse a `ENTITY_TABLE_MAP` (nombre PascalCase → tabla).
- `base44.functions.invoke(nombre)` se traduce a una **RPC de Postgres** vía `FUNCTION_MAP`.
- `vite.config.js` ya no usa `@base44/vite-plugin` (2026-10-05; no agregaba nada al sitio publicado). Ese plugin ponía el atajo `@/` → `src/`: ahora se declara a mano en `resolve.alias`; no lo quites o el build falla con "failed to resolve import @/App.jsx".
- Las carpetas `base44/` (entidades `.jsonc`, funciones) son **código legado de referencia**. **No son fuente de verdad**: el esquema real está en Supabase y esos archivos están desactualizados (columnas que existen en la base no aparecen ahí). Consulta la base real.
- **Stripe / productos digitales / cobros** (`DoctorProduct`, `ProductSale`, `/panel-medico/productos`, `/pagos`, `/dr/:slug/producto/...`) están **fuera de alcance y dormidos**: llamarlos lanza un error a propósito.

### Variables de entorno

`.env` (no se sube a git) necesita: `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY` (obligatorias), y opcionalmente `VITE_GOOGLE_MAPS_API_KEY` y `VITE_GOOGLE_MAP_ID` (mapas, ver sección 8b; sin ellas el sitio funciona pero sin mapa ni autocompletado). La anon key de Supabase es pública por diseño; la llave de Google también va en el navegador y se protege en Google Cloud con restricción de sitio (buscoundoctor.com, localhost) y de APIs, no ocultándola. Las mismas variables deben existir en Vercel. **Jamás** pongas la *service role key* en el repo ni en el frontend.

Para correrlo: `npm install` y `npm run dev` (Vite, puerto 5173). También existe `npm run build`, `lint` y `typecheck`. **No hay suite de pruebas**: se verifica a mano en el navegador.

## 4. Modelo de datos (fuente de verdad: Supabase)

Las tablas están en `snake_case`. Las principales:

- **`specialist`**: la **única** entidad de médico. Nunca crees otra (existió una tabla `Doctor` duplicada; se eliminó).
- Relacionadas con el médico: `office`, `office_hours`, `specialist_document`, `specialist_education`, `specialist_language`, `specialist_service`, `specialist_highlight`, `specialist_case`, `specialist_post`, `specialist_seo_checklist`.
- Catálogos: `specialty`, `subspecialty`, `condition`, `zone`, `insurer`, `language`, `plan`, `hospital` (ver §8n).
- Contenido: `blog_post`, `faq_page`, `faq_item`.
- Interacción: `review`, `appointment_request`, `doctor_contact`, `doctor_click`, `doctor_impression`, `newsletter_subscriber`, `specialty_interest_signup`.
- Panel del doctor / extras: `doctor_storefront` (+ `storefront_*`), `consult_summary`, `consult_review`, `premium_status`, `premium_payment`.
- Operación: `profiles` (rol de cada usuario), `activity_log`, `email_log`, `site_settings`.

### Reglas importantes de `specialist`

- **Vínculo usuario ↔ médico:** `owner_user_id` es el **único** mecanismo. Úsalo para todo "¿este perfil es del usuario logueado?".
- **Visibilidad pública requiere DOS cosas:** `publication_status = 'published'` **y** `active = true`. `active` es un interruptor que **solo el admin** puede cambiar (barra lateral del editor de admin). Un perfil "aceptado" pero con `active=false` no aparece en el sitio.
- `publication_status`: `draft` / `pending_review` / `published` / `suspended` / `rejected`.
- Cédula: `professional_license_number` (único) y `license_verification_status` (`pending`/`verified`/`rejected`). Aprobar un `specialist_document` de tipo `cedula_profesional` la marca `verified` automáticamente (trigger). El badge público "Verificado" depende **solo** de `license_verification_status === 'verified'`.
- `insurers_relation` (array de IDs de `insurer`) reemplazó al texto libre `insurers`; no lo recrees. `certifications` y los campos de un solo consultorio (`address`, `city`, `zone`) son legado: usa `specialist_education` y `office`.
- `has_seen_welcome_tour` controla el popup de bienvenida del panel del doctor.
- Un trigger protege columnas sensibles de `specialist` (un doctor no puede editar verificación, `active`, `featured`…); el frontend además las excluye con `DOCTOR_RESTRICTED_FIELDS`.

### `review`

`rating` general (1–5) más opcionales `rating_punctuality`, `rating_treatment`, `rating_facilities`, y `photo_url`. Cualquiera puede insertar una reseña (sin login) solo con `approved=false`; el admin la aprueba en `/admin/resenas`.

### Roles

Guardados en `profiles.role`: `doctor` (por defecto, lo crea un trigger al registrarse en Auth) o `admin`. La función `is_admin()` solo reconoce `'admin'`. No hay un rol "superadmin" real aunque algún código lo mencione.

**El rol solo lo cambia un admin, directo en la base de datos** (policy `profiles_update_admin_only`; el rol por defecto de una cuenta nueva ya es `doctor`). El código del sitio **nunca** debe escribir `profiles.role`: `updateMe()` en `base44Client.js` ignora el campo `role` a propósito. Antes, `RegistroMedico.jsx` llamaba `updateMe({ role: "doctor" })` al terminar el registro; para un doctor normal no hacía nada (la policy lo bloqueaba), pero a un **admin** que se registraba como doctor con su misma cuenta sí le cambiaba el rol a `doctor` y perdía el acceso a `/admin` (le pasó a Jorge el 2026-10-02; se le restauró a mano en Supabase). Una misma cuenta puede ser admin **y** dueña de un perfil de doctor: `is_admin()` se fija solo en `profiles.role`, no en si tiene perfil.

## 5. Seguridad: RLS y Storage

Todo está protegido con **Row Level Security** en Postgres. Un doctor solo puede ver/editar filas cuyo `owner_user_id` sea el suyo (verificado con cuentas reales el 2026-09-17), o de tablas hijas vía `is_specialist_owner()`. El admin puede todo vía `is_admin()`.

**Storage** (buckets):

| Bucket | Público | Quién sube |
|---|---|---|
| `specialist-photos`, `specialist-videos` | sí | dueño autenticado, en carpeta = su `auth.uid()`; más la carpeta fija `pending-registro/` que acepta subidas **sin sesión** (el registro sube fotos antes de crear la cuenta) |
| `specialist-documents` | **no** (URLs firmadas) | dueño o admin, carpeta = `specialist_id` |
| `review-photos` | sí | cualquiera (sin login), porque quien reseña no inicia sesión |
| `blog-images`, `site-assets` | sí | solo admin |

**Límites por bucket (2026-10-05):** cada bucket tiene tamaño máximo y tipos permitidos (se configuran en `storage.buckets`, no en el código): `review-photos` 5 MB y `specialist-photos` 8 MB (solo imágenes: jpeg, png, webp, heic, heif, avif); `specialist-videos` 50 MB (mp4, mov, webm; 50 MB es también el tope global de subida del plan gratuito de Supabase, así que subirlo no serviría de nada sin plan Pro); `specialist-documents` 10 MB (PDF e imágenes); `blog-images` 5 MB y `site-assets` 10 MB (imágenes; `site-assets` también svg/ico); `admin-guides` y `doctor-products` 20 MB (PDF e imágenes). Evita que alguien use los buckets públicos (sobre todo los que aceptan subidas sin sesión) como hospedaje gratis o para esconder archivos ejecutables/HTML. Ojo: Storage valida el tipo que **declara** quien sube, no el contenido real. `src/lib/storage.js` traduce los errores 413/415 a mensajes en español. **Si un flujo nuevo sube otro tipo de archivo (ej. Word, audio), agrégalo al bucket en `storage.buckets.allowed_mime_types` o fallará con "Este tipo de archivo no está permitido".** Se podría subir el límite del bucket más allá de 50 MB solo con plan Pro.

`base44.integrations.Core.UploadFile({ file, bucket, folder })` sube archivos; pasa por `fileToWebP()` antes (recorta a 1600px y comprime). **Si un formulario público necesita subir archivos, revisa primero la política de Storage**: las subidas sin sesión fallan en silencio (400) si no hay una política que las permita.

### Trampa de permisos en funciones de Postgres

Una función nueva recibe `EXECUTE` por **dos caminos** (el rol `PUBLIC` y los privilegios por defecto de Supabase). Para restringirla hay que revocar **ambos** y verificar con `has_function_privilege`. Revocar solo uno deja la función expuesta.

## 7. Autenticación y correo

- **Registro/login:** Supabase Auth con correo + contraseña. El registro (`/registro-medico`, 3 pasos: datos → ubicación → cuenta; las fotos se suben después desde el panel, ver §8f) y la **recuperación de contraseña** (`/olvide-contrasena`) usan **códigos numéricos por correo (OTP)**, **no enlaces mágicos**. Motivo: Gmail/Outlook "previsualizan" los enlaces y consumen el token de un solo uso antes de que la persona haga clic. **Para cualquier verificación de un solo uso, usa código escrito, nunca un enlace.**
- **Contraseñas (2026-10-06, a petición de Jorge; solo para quien crea cuenta con correo, no para Google/Microsoft):** reglas en `src/lib/passwordRules.js` — **10 caracteres como mínimo, una mayúscula, una minúscula y un número, y que no sea el correo ni una contraseña común o adivinable** (sin símbolos obligatorios a propósito: a muchos médicos les estorban). Se muestran en vivo con `PasswordChecklist.jsx` (lista que se va palomeando + barra Débil/Casi/Segura/Muy segura) y `PasswordInput.jsx` (ojito para ver lo escrito); el botón queda desactivado hasta cumplir todo y repetir la contraseña. Se usan en los 4 lugares donde se crea una: registro (`RegistroMedico.jsx`, pantalla "Crea tu contraseña"), `OlvideContrasena.jsx`, y el cambio de contraseña de Ajustes del médico (`AccountSettings.jsx`) y de Mi cuenta de los dueños (`AdminAccountSettings.jsx`). **Cualquier lugar nuevo que cree una contraseña debe usar esos mismos componentes.** **OJO — estas reglas solo viven en el navegador y se saltan llamando la API de Auth directo:** para que valgan hay que activar la misma política en **Supabase → Authentication → Sign In / Providers → Email → contraseña (largo mínimo 10 y requerir mayúsculas, minúsculas y números)**. Eso se configura en el panel de Supabase, no en el código (pendiente de confirmar que quedó activado); la protección contra contraseñas filtradas (HaveIBeenPwned) es solo del plan Pro.
- Las plantillas de esos correos se editan en Supabase → Authentication → Email Templates (muestran `{{ .Token }}`).
- **Correos transaccionales** (bienvenida, perfil aprobado, nueva solicitud de cita, etc.): la RPC `send_transactional_email` valida el tipo contra una lista fija, resuelve el destinatario **dentro de Postgres** (nunca confía en el cliente), limita el ritmo, envía por **Resend** vía `pg_net` y registra en `email_log`. La llave de Resend vive en Supabase, no en el repo. Los avisos de contacto público e interés en especialidades llegan al correo del dueño.
- **Edge Functions** desplegadas: `create-doctor-profile`, `serve-sitemap-xml`. `/sitemap.xml` se reescribe hacia esta última en `vercel.json`.

### Acceso para un asistente

Un médico puede invitar a **una** persona (secretaria, asistente) para que entre a su panel con su propia cuenta. Decisión de alcance (2026-09-22, aprobada por Jorge): el asistente puede ver y editar **casi todo** (perfil, documentos, consultorios, citas, reseñas, correos, vacaciones) **igual que el dueño**, pero **no** puede cambiar la contraseña/correo del dueño, pedir la baja del perfil, descargar los datos, ni invitar/quitar a otro asistente — esas cuatro cosas viven solo en la pestaña "Mi cuenta", que ni siquiera se le muestra.

- **Tabla `specialist_assistant`** (`specialist_id` único — un solo asistente por médico — `user_id` único, `email`). Sin policies de insert/update/delete: con RLS activo y ninguna definida, esas operaciones quedan bloqueadas para todos salvo las dos RPC de abajo (SECURITY DEFINER).
- **`is_specialist_owner(specialist_id)`** (la función central que ya usaban ~46 policies de tablas hijas — `office`, documentos, formación, citas, reseñas, storefront, notificaciones…) ahora también reconoce a un asistente. Fue el cambio de más apalancamiento: extenderla ahí arregló todas esas tablas de un solo golpe, sin tocar cada policy. Las policies propias de `specialist` (select/update) se homologaron para usarla también (antes tenían el chequeo del dueño repetido en línea).
- **`get_my_specialist_id()`**: para las funciones que antes solo reconocían al dueño por `owner_user_id = auth.uid()` y ahora también deben aceptar al asistente (`start_vacation`, `end_vacation`, `resubmit_for_review`); `mark_doctor_notifications_read` se cambió para usar `is_specialist_owner()` directo.
- **Fotos y video (`specialist-photos`, `specialist-videos`)**: la carpeta de Storage sigue siendo el `auth.uid()` del **dueño** (no se movió ni renombró ningún archivo existente). Para que el asistente pueda subir ahí, se agregó `can_write_specialist_media(owner_uid)` (dueño, o asistente de ese dueño, o admin) en las 6 policies de esas dos buckets, y `base44Client.js` (`uploadFile`) resuelve la carpeta correcta: si quien sube no es dueño de ningún perfil, busca su fila en `specialist_assistant` y usa el `owner_user_id` del médico, no su propio uid. Documentos y productos ya usaban `specialist_id` como carpeta con `is_specialist_owner()`, así que no necesitaron cambios.
- **Invitar** (`invite_specialist_assistant(email)`, botón "Invitar" en Mi cuenta): valida el correo, rechaza si el médico ya tiene asistente, si el correo es el suyo propio, si ya es dueño de otro perfil, si es del equipo (admin), o si ya es asistente de otro médico. Si el correo no tiene cuenta, la crea (mismo patrón que las cuentas QA/David: contraseña aleatoria que nadie conoce, `email_confirmed_at = now()`, campos de token en `''`) y le manda un correo explicando que debe entrar a `/olvide-contrasena` con ese correo para poner su propia contraseña. `crypt()`/`gen_salt()` viven en el esquema `extensions`, no en `public` — hay que calificarlos (`extensions.crypt(...)`) porque estas funciones fijan `search_path` a solo `'public'` por seguridad.
- **Quitar acceso** (`remove_specialist_assistant()`, solo dueño): borra la fila de `specialist_assistant`. Es inmediato — probado que, apenas se borra, un `UPDATE` del ex-asistente sobre `specialist` afecta 0 filas — pero **no** borra la cuenta de `auth.users` (puede volver a invitarse a la misma persona después).
- Ambas RPC (`invite_specialist_assistant`, `remove_specialist_assistant`) comprueban `owner_user_id = auth.uid()` directo, nunca `is_specialist_owner()`/`get_my_specialist_id()`: un asistente no puede invitar a otro ni quitarse el acceso a sí mismo (verificado).
- El panel (`DoctorPanel.jsx`) resuelve "¿de quién es este panel?": primero busca `Specialist.filter({owner_user_id})`; si no hay nada, busca su fila en `specialist_assistant` y carga ESE `specialist_id`. Guarda `isAssistant` y se lo pasa a `DoctorSettings`, que oculta la pestaña "Mi cuenta". ## 8c. Programa de referidos ("invita a un colega")

Decisión de negocio (2026-09-22, aprobada por Jorge) para atacar el cuello de botella real: reclutar médicos. Cada médico tiene un código único; si invita a otro médico que se registra con ese código **y su perfil queda aprobado**, el que invitó gana **1 mes de Premium** — aunque Premium hoy esté apagado (`SHOW_PREMIUM=false`) y sin cobros (Stripe dormido), el mes se acumula en `premium_status.trial_ends_at` para cuando se active. El premio es para quien **invita**, no para quien se registra.

- **`specialist.referral_code`** (6 caracteres, alfabeto sin 0/O/1/I/L para que se lea fácil por WhatsApp o en voz alta), único, generado solo por `generate_referral_code()` (revocada de `public`/`anon`/`authenticated` — nadie la llama directo). Todos los médicos que ya existían recibieron uno al aplicar la migración.
- **`specialist.referred_by_id`** (a qué médico se le atribuye la invitación) y **`referral_rewarded_at`** (evita pagar el premio dos veces si el perfil se pausa y se vuelve a publicar).
- **Captura en el registro:** un campo opcional "¿Te invitó otro médico?" al final de `StepDatos.jsx`, con validación en vivo vía `validate_referral_code(code)` (RPC pública, sin exponer nada del médico salvo su nombre) que muestra "Fuiste invitado por Dr. X". Un código inválido o vacío **nunca bloquea el registro** — se ignora en silencio. `RegistroMedico.jsx` lee `?ref=CODIGO` de la URL para precargarlo (así funciona el enlace de invitación de un clic). `create_doctor_profile` resuelve el código a `referred_by_id` una sola vez, sea que el perfil se cree de cero o se reclame desde un borrador (`saveRegistrationDraft` no necesitó cambios: el código va en el payload final).
- **El premio NO se acredita solo (decisión explícita de Jorge, 2026-09-22).** Aprobar al invitado (o que su perfil se vuelva visible por cualquier otro camino) no toca `premium_status` ni manda nada — solo dispara los avisos normales de siempre. El **equipo decide y acredita a mano** con `credit_referral_reward(specialist_id)` (SECURITY DEFINER, revisa `is_admin()` ella misma además de estar revocada de `public`/`anon` — verificado que un doctor normal la llama y le rechaza "No autorizado"). Esa función exige que el invitado ya esté `published`+`active` y que no se le haya pagado antes (`referral_rewarded_at is null`); entonces le suma 30 días a `trial_ends_at` de quien invitó (se acumulan si invita a varios), le manda un aviso en la campana (`referido_premiado`, ícono de regalo) y un correo (`referido_aprobado`, respeta la preferencia `estado`).
- **Dónde lo acredita el equipo:** una cola nueva en la **Bandeja** ("Premios de referidos por acreditar", `AdminInbox.jsx` — cuenta en el número rojo vía `pendingCounts.js`) con un botón por cada invitado ya publicado, y el mismo botón aparece directo en la pantalla de revisión (`AdminDoctorReview.jsx`) cuando corresponde, para no tener que ir a buscarlo aparte.
- **"Invita a un colega"** (pestaña Compartir, `ShareProfile.jsx`): el código propio, el enlace `/registro-medico?ref=CODIGO`, un mensaje de WhatsApp, y dos números — **"Colegas invitados"** (todos, cuenten o no con premio todavía) y **"Llevas ahorrado"** (solo los ya premiados × el precio del plan Premium, leído de `plan.price_monthly` en vivo, no un número fijo en el código) — y debajo el detalle de cada invitado con su estado ("Esperando aprobación" / "Premio acreditado"). Usa `list_my_referrals()` (RPC propia) en vez de leer `specialist` directo, porque un médico no puede ver el perfil de otro que todavía no está publicado.
- **Correo a quien invitó:** ya estaba desde que se armó `credit_referral_reward` — cuando el equipo acredita el premio, el correo `referido_aprobado` (plantilla "¡Ganaste un mes de Premium!") se manda solo, como parte de esa misma función. Verificado con una prueba real: queda en `email_log` con `status = 'sent'` al correo de quien invitó.
- El admin ve "🎁 Invitado por [nombre]" en la pantalla de revisión (`AdminDoctorReview.jsx`) cuando aplica.
- **Panorama para el equipo** (`/admin/referidos`, `AdminReferidos.jsx`): invitaciones totales, premios acreditados, esperando acreditar, valor acreditado; ranking de quién ha invitado más; y la lista completa de referidos con el mismo botón "Acreditar" que ya existe en la Bandeja y en la revisión individual (misma RPC, tres entradas). El admin no necesita `list_my_referrals()` aquí — `is_admin()` ya le deja ver todo con `Specialist.list()` normal.
- Migraciones aplicadas en Supabase (no están en git): `doctor_referral_program`, `list_my_referrals_rpc`, `referral_reward_manual_not_automatic`.

## 8i. Registro con Google / Microsoft (2026-09-24)

En el último paso del registro (`/registro-medico`), además de "Registrarme con correo electrónico", ahora hay botones **"Continuar con Google"** y **"Continuar con Microsoft"**. La mayor parte de esto ya existía a medias desde la época de Base44 (`base44.auth.loginWithProvider`, la lógica de "regresé autenticado, retoma el registro" en `RegistroMedico.jsx`) — nadie los había conectado a un botón real.

- **Los botones solo se muestran si el proveedor ya está configurado en Supabase.** `RegistroMedico.jsx` le pregunta a Supabase al cargar la página (`GET /auth/v1/settings`, endpoint público, no necesita sesión) qué proveedores están prendidos (`external.google`, `external.azure`) y solo pinta el botón correspondiente si es `true`. Esto es a propósito: sin este checkeo, un doctor real habría podido caer en una pantalla de error en inglés de Supabase ("Unsupported provider") si le daba clic a un botón sin configurar -- con esto, el botón aparece solo, automáticamente, el día que se configure la llave, sin tener que tocar código ni volver a publicar el sitio.
- **`src/lib/supabaseClient.js`** ahora exporta `supabaseUrl` y `supabaseAnonKey` (antes solo el cliente ya armado) para poder llamar ese endpoint de settings desde `RegistroMedico.jsx`.
- **Flujo del lado de código (ya existía, solo se conectó):** al darle clic, se guarda todo lo que el wizard llevaba capturado (`data`) en `localStorage` (`buscoundoctor_pending_registro`) y se llama `base44.auth.loginWithProvider('google' | 'microsoft', returnUrl)`, que hace `supabase.auth.signInWithOAuth(...)` -- esto navega el navegador completo a Google/Microsoft y de regreso a `/registro-medico` ya autenticado. ## 8j. "Dudas solucionadas" -- preguntas y respuestas en el perfil (2026-09-30)

Sección nueva en el perfil público, inspirada en Doctoralia: un visitante pregunta algo sin necesidad de cuenta (igual que una reseña) y el doctor la responde desde su panel. **A diferencia de las reseñas, no hay aprobación de un admin de por medio** -- una pregunta nunca se hace pública hasta que el propio doctor la contesta, así que no le agrega trabajo al equipo de BuscoUnDoctor.

### Secuestro y vandalismo de perfiles por el id del "borrador" (2026-10-08)

**Hueco crítico encontrado y cerrado** (al preparar la función de "reclamar perfil"; nadie lo había explotado: hoy no había médicos publicados):

- **`create_doctor_profile(draft_id)`** reclamaba el "borrador" que dijera el cliente con `update … where id = v_draft_id`, **sin comprobar que fuera un borrador libre**. Cualquier cuenta (basta crear una con un correo) podía pasarle el `id` de **cualquier médico** —los `id` de los perfiles son públicos— y quedarse como dueña: cambiaba el nombre y lo ocultaba (`active = false`). Probado con datos de prueba: el "atacante" se quedó con el perfil publicado de la "víctima".
- **`save_registration_draft(draft_id)`** (la puede llamar **cualquiera, sin cuenta**) hacía lo mismo con `update … where id = v_specialist_id`: un visitante podía sobrescribir nombre, WhatsApp, especialidad, cédula, dirección y fotos de **cualquier médico** (por ejemplo, desviar los WhatsApp de los pacientes). Probado: se cambió el WhatsApp y la cédula de un perfil publicado.
- **Arreglo:** las dos funciones (y `get_registration_draft`, que además filtraba datos por id) ahora solo operan sobre **borradores del registro**: `owner_user_id is null` **y** `publication_status = 'draft'` **y** `registration_step is not null`. Si el id no cumple, se crea un borrador nuevo y el perfil ajeno no se toca. Verificado: los dos ataques ya no cambian nada (perfil intacto) y el registro legítimo sigue igual (guardar y actualizar el mismo borrador, recuperarlo por su id, y crear la cuenta reclamando su borrador). ### Anti-spam en los formularios públicos (2026-10-05)

Antes **cualquiera** podía mandar sin límite citas, reseñas, preguntas, mensajes de contacto, interesados, boletín y borradores de registro (cada uno dispara avisos y correos a doctores o dueños), y además podía fijar campos que no le tocan. Los triggers `<tabla>_0_guard` (BEFORE INSERT) aplican los límites; el `0` es para que corran antes de otros triggers (por ejemplo `trg_verify_review_client`).
- **Límites (por IP salvo que se diga):** cita 8/hora y 25/día, 20/hora por doctor y 5/día por correo y por teléfono; reseña 5/hora y 15/día, 10/hora por doctor y **2/día por doctor desde una misma IP**; pregunta 5/hora y 15/día, 15/hora por doctor y 3/hora por doctor desde una IP; interés en especialidad 10/hora y 30/día, 3/día por correo; boletín 10/hora y 30/día, 3/día por correo; contacto del sitio 5/hora y 15/día, 5/día por correo; borradores de registro 60 guardados/hora y 10 borradores nuevos/hora (30/día); código de invitación 60/hora; baja de correos 20/hora. Vistas y clics (`doctor_impression`, `doctor_contact`, `doctor_click`): son **silenciosos** (al pasarse, la fila simplemente no se guarda, sin error en pantalla): vistas 400/hora y 5/hora por doctor, contactos 60/hora y 10/hora por doctor, clics 120/hora y 20/hora por doctor. Para cambiar un número: editar la función `trg_guard_*` correspondiente en Supabase y anotar la migración aquí.
- **Mensajes:** al pasarse, la base responde con un texto **ya en español** y código `P0001` (demasiadas solicitudes: "Has enviado muchas solicitudes seguidas. Intenta de nuevo en un rato.") o `22023` (datos no válidos / texto demasiado largo). `src/lib/formErrors.js` (`formErrorMessage`) lo muestra en `AppointmentForm`, `ReviewForm` (antes, si fallaba, se quedaba "cargando" para siempre), `QuestionForm`, `SpecialtyInterestForm`, `Contact` y `BookingFlow` ya mostraba `e.message`. - **Campos que el visitante ya no puede fijar** (se comprobó antes y después con una reseña de prueba): en `review`, el sello `verified_client` (antes bastaba mandar `true` para tener "Cliente verificado"), `doctor_reply`/`doctor_reply_at` (una respuesta del doctor inventada), `approved`, `rejected`, `reviewed_*`, `owner_user_id`; `photo_url` solo puede ser de nuestro bucket `review-photos` (si no, se descarta); `consultation_date` no puede ser futura. ## 8o. Perfiles armados por el equipo que el doctor reclama (2026-10-08)

Idea de Jorge para atacar el cuello de botella (reclutar): el equipo arma el perfil de un doctor (nombre, especialidad, cédula, consultorio, servicios) y el doctor solo lo "reclama". **Opción A, decidida por Jorge: el perfil es PRIVADO hasta que el doctor lo reclama** (no se publica "sin reclamar"; los datos los arma el equipo a mano, no se copian de Doctoralia ni de otros sitios).

- **Cómo se arma:** un admin crea el doctor en `/admin/doctores/nuevo` ("Guardar como borrador"). Vence a los 30 días. "Desactivar enlace" lo anula. Si se sale de la pantalla y se vuelve, la tarjeta avisa "Ya hay un enlace activo (vence el …)" y deja **Desactivar enlace** (no se puede volver a ver el enlace; solo reemplazarlo o desactivarlo). Cuando el doctor reclama, la tarjeta dice "El doctor reclamó este perfil el …".
- **Columnas nuevas en `specialist`:** `claim_token_hash` (único), `claim_token_expires_at`, `claimed_at`, `seeded_by_admin`. Un doctor no puede cambiarlas (las congela `protect_specialist_admin_columns`; también están en `SERVER_MANAGED_FIELDS`). El rol `anon` no las ve (no están en `SPECIALIST_PUBLIC_COLUMNS`).
- **RPC (todas `SECURITY DEFINER`):**
  - `generate_claim_link(specialist_id)` y `revoke_claim_link(specialist_id)`: solo admin (`is_admin()`, revocadas de `public`/`anon`). Rechazan perfiles que ya tienen dueño o están en la papelera. Dejan `enlace_reclamo_generado` en el Historial.
  - `get_claim_preview(token)`: pública (la usa la pantalla antes de iniciar sesión). Devuelve nombre, especialidad, consultorios, servicios y solo los **últimos 3 dígitos de la cédula**; límite 40/hora por IP. Para token inválido/vencido responde `{ok:false, reason}` sin distinguir si existió.

Si el perfil tiene cédula capturada, hay que escribirla completa (se compara sin espacios ni guiones, sin importar mayúsculas); si no tiene cédula, el enlace solo es la llave (la tarjeta del admin lo avisa). ## 8p. Vista previa al compartir un perfil (WhatsApp, Facebook, iMessage…) (2026-10-08)

Idea de Jorge: que al compartir el enlace de un doctor salga una tarjeta con su foto y sus datos. **El problema real era que no salía:** WhatsApp, Facebook, iMessage, Telegram, LinkedIn, X, Slack y Discord leen la página **sin ejecutar código**, y el sitio es una aplicación que pone el título y la foto del doctor *después* de cargar (`setOpenGraph` en `SpecialistProfile.jsx`), así que esas apps veían siempre la tarjeta genérica del inicio (comprobado pidiendo un perfil con el user-agent de WhatsApp). `setOpenGraph` sigue sirviendo para Google y para las personas; no lo quites.

- **Cómo funciona:** `vercel.json` tiene una regla (`rewrites`, antes del comodín `/(.*)`) que manda `/especialista/:slug` a la función `api/og.js` **solo cuando el user-agent es de una de esas apps** (`facebookexternalhit|Facebot|WhatsApp|Twitterbot|TelegramBot|LinkedInBot|Slackbot|Slack-ImgProxy|Discordbot|Pinterest|SkypeUriPreview|Applebot|redditbot`). Las personas y Google (que sí ejecuta el sitio) reciben la aplicación de siempre; **no se agregó Googlebot a propósito** (mostrarle a Google algo distinto a lo que ve una persona sería encubrimiento). iMessage de Apple se hace pasar por `facebookexternalhit`/`Twitterbot`, por eso entra por la misma regla.
- **`api/og.js`** devuelve una página mínima con título, descripción, `og:image` y `twitter:card = summary_large_image`. **Los textos se arman en un solo lugar, `src/lib/profileMeta.js` (sin imports; lo usan también `SpecialistProfile.jsx` para la pestaña y Google, y `api/_lib/og.js` importa ese archivo desde el servidor):**
  - **Título de la pestaña/Google:** `Nombre — Especialidad en Zona | BuscoUnDoctor`. **El título de la tarjeta (`og:title`) va sin "| BuscoUnDoctor"** (WhatsApp ya muestra el dominio debajo).
  - **Especialidad = el nombre "como lo busca el paciente"** del catálogo (`specialty.display_name`: "Cardiólogo"), que se pasa a **femenino cuando el nombre empieza con "Dra."/"Doctora"** (`genderSpecialty`: toda palabra que termina en "o" cambia a "a": Cardióloga, Cirujana Plástica, Médica General; Pediatra, Dentista, Psiquiatra… no cambian). Revisado con las 64 especialidades del catálogo. Si la especialidad nueva del catálogo no sigue esa regla, revisar `genderSpecialty`.
  - **Descripción** (máx. 160, cortada en límite de palabra con "…"): `⭐ 4.9 (N reseñas) · ` si hay reseñas aprobadas + la presentación que escribió el doctor (sin formato) o, si no escribió, el texto genérico `Especialista en <especialidad formal> en <Zona>. Contacta directo y agenda tu cita.`; **solo agrega "Cédula profesional verificada." cuando `license_verification_status = 'verified'`** (antes lo decía siempre, aunque no estuviera verificada).
  - Los textos genéricos con "cédula profesional verificada" de **otras páginas** (Hospitales, Inicio, `TrustBadges`) hablan del sitio en general o de los perfiles que sí lo están; no se tocaron. Lee con la **llave anon** (la misma pública del sitio): la base de datos misma garantiza que un perfil que no está `published` + `active` (borrador, en revisión, en pausa, armado por el equipo sin reclamar —§8o—) **no devuelve nada**, y entonces sale la tarjeta genérica del sitio, sin ningún dato del doctor. Se cachea 1 hora (`s-maxage`). Si algo falla, también cae a la genérica: nunca devuelve error.
- **`api/og-image.js`** genera la imagen. **Con foto: CUADRADA 1200×1200 que ocupa toda la tarjeta** (como Doctoralia, a petición de Jorge tras verla en WhatsApp: primero se probó la foto centrada sobre un fondo gris difuminado y luego sobre un fondo con el logo repetido; Jorge prefirió la foto grande), con el **logo de BuscoUnDoctor en una píldora blanca abajo a la izquierda**. Si la foto es **vertical** se recorta **anclada arriba** (la cabeza casi siempre queda arriba; el recorte automático "por atención" de `sharp` le **cortó la cabeza** a una foto real vertical, por eso no se usa); si es horizontal o cuadrada, centrada. Una foto muy fuera de lo común (cuerpo entero, cabeza abajo) podría recortarse mal: si pasa, hay que ajustar esa foto o la regla. **Sin foto (o si algo falla): tarjeta 1200×630 con el logo sobre blanco.** Reduce el peso porque **las fotos de los doctores pueden pesar varios MB** (la real del Dr. Pacheco pesaba 2 MB; la tarjeta resultante, ~100 KB) y WhatsApp no muestra imágenes pesadas. Solo descarga fotos de nuestro propio Storage público (`…/storage/v1/object/public/`), nunca una URL cualquiera. El logo (`site-assets/email-logo.png`) tiene fondo **transparente** (sirve sobre cualquier color). La URL de la imagen lleva `&v=<fecha de actualización del perfil>` y `&d=3` (versión del diseño): **si vuelves a cambiar el diseño, sube ese número** en `api/og.js` para que el CDN y WhatsApp la pidan de nuevo (con `v` la respuesta se cachea un año). `og:image:height` sale 1200 con foto y 630 sin foto.
- **Dependencia nueva: `sharp`** (solo la usa `api/`, no llega al navegador del visitante). `api/_lib/og.js` (el guion bajo evita que Vercel lo exponga como ruta) junta lo compartido. Las variables `VITE_SUPABASE_URL` y `VITE_SUPABASE_ANON_KEY` que ya existen en Vercel sirven también para estas funciones; sin la llave, la función responde la tarjeta genérica.
- **Tarjeta de los enlaces de reclamo (`/reclamar/:token`, §8o):** una segunda regla de `vercel.json` (mismos user-agents) manda esos enlaces a `api/og.js?tipo=reclamar`, que devuelve una tarjeta **fija**: título "Reclama tu perfil en BuscoUnDoctor", el logo y un texto corto, con `noindex`. **A propósito no consulta la base ni muestra el nombre ni ningún dato del doctor:** el perfil es privado y el enlace se puede reenviar. El token solo se repite en la dirección (validado a `[A-Za-z0-9_-]{20,80}`; si no cumple, se usa la raíz). Antes salía la tarjeta genérica del inicio, sin imagen.
- **Botón "Compartir"** (`ShareProfileButton.jsx`): ahora comparte el enlace limpio `https://buscoundoctor.com/especialista/<slug>` (antes era `window.location.href`, con `#ancla` y parámetros).
- **Límites conocidos:** (1) WhatsApp/Facebook guardan en memoria la tarjeta de cada enlace: uno compartido antes de este cambio puede seguir saliendo genérico por días (Facebook tiene el "Depurador de uso compartido" para forzar la actualización; WhatsApp no). (2) Solo perfiles de médicos; hospitales y blog siguen con la tarjeta genérica (se puede repetir el mismo patrón). (3) Si un doctor no tiene foto sale el logo, no su nombre en la imagen (no hay fuentes en el servidor para dibujar texto). (4) Para probar: `curl -s -A "WhatsApp/2.23" https://buscoundoctor.com/especialista/<slug> | grep og:` debe traer el nombre del doctor y `og:image` con `/api/og-image?slug=…`; sin ese user-agent, el HTML del sitio de siempre.
- Sin cambios de base de datos.

## 9. Cómo probar sin ensuciar producción

Como no hay staging, el patrón acordado es: **crear datos de prueba, verificar, y borrarlos siempre al terminar**, confirmando con un `count(*)` que quedó en 0. Reglas:

- Cuentas de prueba: crea `auth.users` + `auth.identities` con SQL (`crypt(pass, gen_salt('bf'))`, `email_confirmed_at = now()`), pon el rol en `public.profiles`, y (si es doctor) crea su fila en `specialist` con `owner_user_id`. **Los campos de token de `auth.users` (`confirmation_token`, `recovery_token`, `email_change`, `email_change_token_new`, `email_change_token_current`, `phone_change`, `phone_change_token`) deben ser `''`, no `NULL`**, o el login falla con "Database error querying schema".
- Borra en orden: `specialist` → `profiles` → `auth.identities` → `auth.users` (y usa el `owner_user_id`, no el `id` del specialist).
- Nombra las pruebas con prefijo `QA` para reconocerlas. Los archivos subidos a Storage no se pueden borrar por SQL; son diminutos y están bien de quedarse.
- Para ver la interfaz: levanta `npm run dev` (puerto 5173; en la app de Claude, `preview_start` con una config `dev` en `.claude/launch.json`, que no está en git: créala si falta) y prueba en móvil (375px), tablet (768px) y escritorio (1440px).
- Para llenar formularios de React desde automatización, los clics y `type` por referencia funcionan; asignar `.value` directo no actualiza el estado de React (usa el setter nativo + evento `input`).

## 10. Trampas conocidas del código

- **Autoguardado (`useAutoSaveSpecialist`, reescrito el 2026-10-04):** ya no hay botón "Guardar cambios" ni guardado cada 30 s. Guarda **solo los campos que cambiaron** (compara contra la última "foto" guardada) 1.5 s después de la última tecla, y de inmediato al ocultar la pantalla (`visibilitychange`/`pagehide`), al cambiar de sección o al salir de la página; si falla muestra el aviso en rojo (cabecera + toast), reintenta a los 10 s y pide confirmar al cerrar la pestaña con cambios sin guardar. Consecuencias: (1) un campo actualizado directo en la base **ya no** se pisa por un autoguardado (solo se manda lo que el usuario tocó), así que el doctor y su asistente ya no se sobrescriben entre sí salvo que editen el mismo campo; (2) los campos que calcula el servidor (`completeness_score`, `seo_score`, `updated_date`…, lista `SERVER_MANAGED_FIELDS`) nunca se mandan de vuelta: si agregas otra columna que el servidor modifica y el formulario refleja, agrégala ahí o se reenviará en cada cambio; (3) el hook devuelve `{ saveState, lastSaved, errorMessage, hasUnsaved, flush }` y el panel muestra "Guardando… / Guardado a las… / No se pudo guardar". Un doctor **nuevo** en el admin (aún sin `id`) conserva "Guardar como borrador" y "Crear y publicar".
- **`overflow-x: hidden` en `html/body` rompe `position: sticky`** (CSS obliga a `overflow-y: auto`). Se usa `overflow-x: clip` en `src/index.css`. No lo cambies.
- Un contenedor flex hijo sin `min-w-0` se estira al ancho de su contenido y provoca scroll horizontal (así se rompió el panel del médico en móvil). En el panel del doctor, la barra de pestañas móvil ahora es un menú hamburguesa.
- **Registro del médico en celular (2026-10-04):** cada paso (y cada pantalla: correo, código, listo) empieza desde arriba; `RegistroMedico.jsx` hace `window.scrollTo(0, 0)` cuando cambia `stepIndex` o `phase`. Antes, como "Siguiente" está al final de una pantalla larga, el paso siguiente se abría ya recorrido hacia abajo. Si agregas otro wizard de varios pasos, haz lo mismo.
- **Registro sin menú ni pie (2026-10-04, a petición de Jorge):** `/registro-medico` se muestra con `<Layout minimal />` (mismo SEO/canonical que el resto, pero sin `Header`, aviso "¿Eres médico? Regístrate aquí" —que salía en la propia página de registro—, buscador de pacientes ni `Footer`). Motivo: en celular el menú con buscador se quedaba pegado arriba y le quitaba más de una cuarta parte de la pantalla al formulario, la página medía 2,709 px y ahora 1,420 px, y el doctor tenía a un toque salirse a buscar especialistas. Los enlaces legales (Aviso de privacidad, Términos) se movieron a una línea al final de la tarjeta. `/iniciar-sesion` y `/olvide-contrasena` siguen con el menú completo (se pueden pasar a `minimal` igual si se quiere). Si agregas otra pantalla de conversión sin distracciones, ponla dentro de `<Route element={<Layout minimal />}>` en `App.jsx`.
- **Sin "Volver al sitio" en los paneles (2026-10-04, a petición de Jorge):** se quitó de los dos paneles (escritorio y celular: `AdminLayout.jsx`, `DoctorPanel.jsx`, `DoctorPanelLayout.jsx`, `DoctorPanelSidebar.jsx`) y el "Sitio" de la barra móvil del doctor. En el panel del doctor en celular el botón ☰ ahora va a la **izquierda** (campana a la derecha) y el menú se abre desde la izquierda, igual que en el admin de dueños. Para ir al sitio público quedan "Mi página pública" (doctor) o escribir la dirección.
- **Sin botones "Vista previa" (2026-10-04, a petición de Jorge):** se quitaron del encabezado del panel del doctor y del editor de doctores del admin, y el interruptor "Editar / Vista previa" de la descripción del doctor (`DoctorEditorPerfil.jsx`, vista completa) y del editor de blog (`BlogEditorMain.jsx`, que ya solo muestra el editor). Para ver el perfil público: "Ver perfil público" en el Inicio del doctor o "Mi página pública". El panel "Vista previa" de la página personalizada (`DoctorStorefrontEditor.jsx`) es un encabezado, no un botón, y no se tocó.
- **Menús laterales en celular: un solo scroll (2026-10-04).** El cajón es el que se desplaza completo (`overflow-y-auto overscroll-contain`), nunca la lista de enlaces por separado: encabezado, enlaces y "Salir" suben y bajan juntos, y el fondo queda bloqueado. Antes, en el panel del doctor la lista tenía su propio `overflow-y-auto` y se sentían varios scrolls. Si agregas otro cajón, el contenedor scrollea y los hijos no.
- **iPhone: la página de atrás se movía con el menú abierto (2026-10-04).** `document.body.style.overflow = "hidden"` **no** bloquea el scroll en Safari del iPhone: al arrastrar sobre la franja oscura junto al menú (o sobre un menú que no desborda) se movía la página de atrás y se sentían "varios scrolls" (el arreglo de arriba solo cubría el scroll interno del cajón, y no se había probado en iPhone). Ahora los dos cajones (`AdminLayout.jsx`, `DoctorPanel.jsx`) usan `src/hooks/useBodyScrollLock.js`, que fija el body (`position: fixed` en el punto de scroll) y restaura la posición al cerrar; el fondo oscuro del admin lleva además `touch-none`. Verificado en el simulador de iPhone 17 Pro (Safari de verdad), no solo en el navegador de escritorio: el simulador se puede arrancar con `xcrun simctl boot` y se abre `localhost:5173` en Safari con `xcrun simctl openurl booted <url>`. **Para cualquier cajón/modal nuevo usa ese hook, no `body.style.overflow`.**
- Si una página se ve "cortada a la derecha" en móvil, compara `document.documentElement.scrollWidth` con `clientWidth`.
- **Confirmaciones "¿seguro?" del admin dueños:** usa `useConfirmDialog()` (`src/hooks/useConfirmDialog.js`) + `<ConfirmDialog {...dialogProps} />` (`src/components/admin/ConfirmDialog.jsx`) — nunca `confirm()`/`window.confirm()` del navegador (se reemplazaron los 16 que quedaban, en 11 pantallas, el 2026-09-22). Patrón: `const { confirm, dialogProps } = useConfirmDialog();` arriba del componente, `const ok = await confirm({ title, description, confirmLabel }); if (!ok) return;` donde antes había un `confirm(...)`, y `<ConfirmDialog {...dialogProps} />` una vez en el JSX. `prompt()` (el único que queda, en `AdminDoctores.jsx` para el motivo opcional de la papelera) no se tocó — reemplazarlo necesitaría un modal con campo de texto, no solo confirmar/cancelar.

## 13. Principio de trabajo más importante: auditar antes de construir

Este proyecto **no se construye desde cero**. Antes de agregar algo:

1. Verifica si ya existe, aunque sea parcialmente (varias veces resultó que un componente ya estaba hecho pero sin conectar, p. ej. el botón Compartir).
2. Si algo parece duplicado o inconsistente, **diagnostica primero** qué tabla/componente tiene datos reales y qué usa la app pública, antes de borrar o fusionar.
3. Un cambio = un commit enfocado. No mezcles datos y UI de temas no relacionados.
4. Toda funcionalidad nueva se verifica con un caso real probado.
5. Las cosas mal ordenadas o rotas que encuentres fuera del alcance: avísalas, no las arregles en silencio.
